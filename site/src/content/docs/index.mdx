<section class="chapter problem">
  <Illus name="problem" />
  <p class="kicker">Why VEW exists</p>
  <h2>Two bottlenecks, one catalog.</h2>
  <div class="two">
    <div>
      <h3>Environment bottleneck</h3>
      <p>Setting up a development environment is hand work, repeated for every developer: a long list of tools, each with its own license and configuration. Every install is different, so when a build breaks on one machine and not on another, the cause is hard to find.</p>
    </div>
    <div>
      <h3>Hardware bottleneck</h3>
      <p>Target hardware arrives late and is shared when it does. Verification queues behind a physical bench. Some ECU combinations can't be assembled on any physical rig. In a V-model process, a developer who changes one component waits for every stage below it.</p>
    </div>
  </div>
  <dl class="numbers">
    <div><dt>6–8 weeks</dt><dd>to set up a development environment</dd></div>
    <div><dt>50+</dt><dd>tools per developer, each with a license</dd></div>
    <div><dt>months</dt><dd>waiting for target hardware</dd></div>
    <div><dt>days</dt><dd>in the queue for a test bench</dd></div>
  </dl>
  <p class="turn">VEW handles both the same way: you <strong>define an environment once and version it</strong>, and then a developer, a pipeline or an agent can launch it. Hardware is still needed, but it no longer gates every change.</p>
  <p class="source">See the <a href={`${b}/what-is-vew/`}>problem in detail</a>.</p>

{/* Chapter 2 · Catalog */}
<section class="chapter catalog">
  <Illus name="catalog" />
  <p class="kicker">Tools, targets, environments</p>
  <h2>Browse, launch, connect, stop.</h2>
  <p class="intro">The portal lists the products your project allows. You pick a stage and a version, and the portal shows the state of each product and how to connect to it.</p>
  <ul class="points cols2">
    <li><strong>Launch and connect.</strong> Choose a product, a stage and a version. After a few minutes the product is running, and you connect to it from the browser.</li>
    <li><strong>Tools, targets and environments.</strong> Tools are what you build with, targets are what you build for, and environments are the test and configuration data that make a result meaningful. The catalog delivers all three: the tools are installed in the image, and workbenches and virtual targets are products you launch.</li>
    <li><strong>Stop at the end of the day.</strong> Stopping a product ends its EC2 compute charges. Its storage remains, and you still pay for that.</li>
    <li><strong>Role-based catalog.</strong> The catalog shows only the products your project and role permit, and Cedar policies enforce that limit on the backend.</li>
  </ul>
</section>

{/* Chapter 3 · Factory */}
<section class="chapter factory">
  <Illus name="factory" />
  <p class="kicker">Package and publish</p>
  <h2>Pipeline images are built and tested in your account.</h2>
  <ul class="points cols2">
    <li><strong>Versioned components.</strong> Each install step is a versioned EC2 Image Builder component. You can compare two versions side by side as YAML.</li>
    <li><strong>Recipes.</strong> A recipe is an ordered list of components on a base OS. Admins pin components per platform, OS and architecture, and VEW adds them to every matching recipe.</li>
    <li><strong>Pipelines build and test.</strong> Each build runs on a new instance. The tests run on it before the image is accepted, and the instance is terminated whether they pass or fail.</li>
    <li><strong>Staged releases.</strong> Publish a version to DEV, test it, then promote it to QA and PROD. Release candidate (<code>-rc</code>) versions let you test before each promotion, and users cannot downgrade by accident.</li>
  </ul>

{/* Chapter 4 · Ways in */}
<section class="chapter ways">
  <Illus name="ways" />
  <p class="kicker">Portal, CLI, APIs and MCP</p>
  <h2>The same product serves a developer, a pipeline and an agent.</h2>
  <p class="intro">A release cycle changes only when every developer and every pipeline runs the same definition. In VEW, one product launches as a developer workspace or as a CI runner with the same configuration, from one click in the portal or one API call.</p>
  <ul class="points cols2">
    <li><strong>The portal</strong> is for people. It is built in React and Cloudscape, and you browse, launch, connect and stop there.</li>
    <li><strong>The <code>vew</code> CLI</strong> is for scripts. It is a single Rust binary that signs in with the deployment's Cognito user pool and derives its commands from the API specifications.</li>
    <li><strong>Service-to-service APIs</strong> are for pipelines. A client holds an OAuth client credential with a scope per operation, and the packaging routes also require a project assignment. A build launches a new target from the same product definition, runs on it, then terminates it.</li>
    <li><strong>The MCP gateway</strong> is for agents. It exposes over 100 tools to an MCP client that speaks HTTP transport and OAuth 2.0 with PKCE. The agent signs in as you, so Cedar policies limit it to what you are allowed to do.</li>
  </ul>
